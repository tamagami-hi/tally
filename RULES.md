# Rules of the harness

What tally enforces, and what it promises. The tracked repository's own rules govern its work; these govern the records.

1. **`docs/records/` is written by the harness alone.** The ledger, the hand-offs, the evidence and the config are JSON records that change only through tally's verbs (the CLI, the MCP tools, or a script that was cut over to them). A hand edit is a bug. The context folder, `docs/records/context/`, is part of the records, and a landing in the queue refuses a commit that changes anything under `docs/records/`.
2. **Progress is counted from `ledger.json` and from git, and from nothing else.** A task is landed when its commit is on main. `ledger_check` lists the commits on main no record names; a landing is finished only when it lists nothing.
3. **One home per fact.** A status, a count or a note is stored once and shown many times: the board, the terminal status, the context packs and the markdown views are computed, never copied.
4. **A session binds to one repository, one worktree and one track.** The path must be the track's worktree on the track's branch. A track session writes only its track's tasks, evidence, hand-off and claims; an operator session (the repository's checkout on its main branch) may write any track. Every session reads everything in its own repository, and nothing in another's.
5. **Claims and locks are live state, not history.** They live outside git and die with their session: in the service's data folder (`<TALLY_HOME>/state/<name>/`) for a repository on its list, and under the repository's `.temp/tally/state/` for one served alone with `--repo`. One task per session; one session per task; a lock is held by one session, released by the holder or with the session; a lock's name must be in the config.
6. **A run record is written once, with its log's hash.** A run made through the runner keeps its log under the repository's `.temp/tally/logs/`, and the service writes the record from the runner's result; a run made with `evidence_run` keeps its log inside the session's worktree. The harness never edits, moves or deletes a log. A report cites records by id.
7. **Records commits are the harness's own.** A change to a record is saved on main as a docs-only commit prefixed `records:`, made with the configured identity, with no hooks and no signature, under the landing lock, so it never moves main under a landing in flight. When it is made is the repository's records mode: at once (`each`), when the last session closes and when a landing finishes (`records.batch`, the `rest` mode), or only by `phase_close` and `records_commit` (`records.commitAt: "phase"`, one commit for the records of a whole phase); never by tally when `records.commit` is false. While a landing has its turn it waits, and goes in when that landing finishes. The check and the status pass over them by their prefix.
8. **Schemas change additively.** Every record carries `"schema": 1`; a reader refuses a schema it does not know and names it; a field is added in one release and removed only after the readers tolerate its absence.
9. **The landing refuses what it cannot vouch for:** the operator's checkout off its main branch, or holding an uncommitted change in a file the landing changes (the refusal names the files, and comes before any check runs), a worktree off its track's branch, staged files the landing was not told about, uncommitted work without a message, a verification fingerprint that no longer matches, tests that fail, and main that moved while the landing ran. In the service the agent runs the checks from a script tally writes, and the landing refuses a result that is missing, failed, or not for the commits being landed. A refused landing changes nothing; a clean landing (`commands.landing`) that had already committed undoes its commit and leaves the files staged.
10. **The harness never pushes, deploys, reads a `.env` or runs `sudo`.** It creates a track's branch and worktree when `track_open` asks, and removes only a worktree and a branch it created, once nothing in them can be lost: a closed worktree takes its ignored build output with it, and what an agent kept under its `.temp/` is moved to `.temp/closed/<track>/`, never deleted. The service closes a track by itself only when its work has landed and it has sat idle. Under `.temp/` it deletes only what is its own: its landing checkouts, what a run left in them, and a file it copied for the service. It commits records and lands by fast-forward. A server of one repository runs the commands it is told to run in the worktree it is bound to, or in that worktree's landing checkout; the service runs none, and the agent runs them from a script tally writes. Pushing is the operator's.
11. **Loopback only.** The server and the MCP endpoint listen on `127.0.0.1`, and the service's container is published on the host's loopback only. A request from another host, or from another site's page, is refused. The one trust is the worktree binding; the machine is the operator's.
12. **Small files, tests first, no comments in source.** Source and test files stay under 400 lines; a behaviour is written with the test that sees it fail first; names carry the meaning comments would.
