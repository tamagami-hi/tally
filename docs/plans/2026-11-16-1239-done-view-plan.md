## 3. Decisions the operator may want to change

Each has a default, and the build follows the default unless the operator says otherwise.

1. **The view is called Done.** It sits after Board: Board, Done, Evidence, Docs on a wide screen; Board, Tracks, Graph, Done, Evidence, Docs on a phone.
2. **A milestone is finished when every task of it has landed on main (or it is marked built) and `ledger_check` lists no gap for it.** A gap is what `ledger_check` already lists: a deliverable no task covers, a deferred part with nowhere to go, a landed task that still needs a review. A part left to a task that exists is no gap, and a parked part is no gap, so neither keeps a milestone on the board. This is the same line `phase_close` draws.
3. **A phase leaves the board when it is closed, not when it reaches 100%.** An open phase whose milestones are all finished stays as one line that says so. Reaching 100% is counted by tally; closing is the operator's act, and the board keeps showing that it is still owed.
4. **Nothing unfinished is ever hidden.** A closed phase that has an unfinished milestone again (a later review with blocking findings, say) is back on the board, marked.
5. **A landed task of a milestone still in progress** stays on the board as part of the count, as today, and is listed in Done under its milestone, which is marked as in progress.
6. **Ended sessions are computed from the activity log.** No list of them is stored, in the records or in the live state (rules 3 and 5). A repository that keeps no activity log lists no ended sessions, and the view says why. To make the log complete, a session's opening and its expiry are logged from now on (Part D).
7. **No MCP tool is added, and no answer loses anything.** `board_get` and `tally status` still answer every milestone. Each row gains `finished`.
8. **The percentages do not change.** Overall and each phase's share still count everything.
9. **The version becomes 0.4.0.**

## 4. Part A: one meaning of "finished"

`MilestoneRow` in `status/summary.ts` gains `finished: boolean`, set in `summarize`:

- `finished` is true when the row's `share` is 1 or more and no gap names the milestone.
- The gaps are `findGaps(ledger)` and the tasks `needingReview` returns. `summarize` already receives the second.
- A landed task whose commit is not on main already lowers `share`, so that milestone is not finished.
- A milestone with no task that is not marked built is not finished.

`rowsOf` (the `scope: "mine"` slice) keeps the milestone's own `finished`, as it keeps the milestone's own `share`.

The page's copy of the type in `packages/web/src/types.ts` gains the same field, and the test fixtures with it.

Tests first, in `packages/core/tests/status/`: built; every task landed and no gap; a deferred part with no target; a part left to a task that is not in the ledger; a part left to a planned task (finished); a parked part (finished); a deliverable no task covers; a landed task that needs a review; a landed commit that is not on main; no tasks and not built.

## 5. Part B: the Done answer for phases, milestones and tasks

A new folder, `packages/core/src/done/`. Its first function builds the answer from the status the board already shows, so the two never disagree:

```ts
interface DoneTask {
  id: string;
  track: string;
  commit: string;
  also: string[];
  at?: string;
  dated?: "recorded" | "commit";
  deferred?: { what: string; to?: string; why?: string; state: "unplaced" | "waiting" | "done" | "parked" }[];
}

interface DoneMilestone {
  id: string;
  name: string;
  track: string;
  finished: boolean;
  built?: string;
  count: [number, number] | null;
  tasks: DoneTask[];
}

interface DonePhase {
  id: string;
  name: string;
  goal?: string;
  state: "open" | "closed";
  closedAt?: string;
  closedBy?: { track: string; agent: string };
  summary?: string;
  commit?: string;
  share: number;
  milestones: { finished: number; total: number };
  tasks: { landed: number; total: number };
  rows: DoneMilestone[];
}

interface DoneWork {
  counts: { phasesClosed: number; milestonesFinished: number; tasksLanded: number };
  phases: DonePhase[];
}
```

The rules:

- **A milestone is listed** when it is finished or has at least one landed task. Its `tasks` are its landed tasks only.
- **A phase is listed** when it is closed or has a listed milestone. Closed phases come first, the latest close first; open phases follow in the board's order.
- **A task's time** is its `landedAt` when the ledger has one (`dated: "recorded"`). Otherwise it is the date of its commit (`dated: "commit"`), read with one git call for the whole answer (`git log` over the ledger's baseline to main, with the hash and the committer date), never one call per task. A commit that is not found leaves `at` out.
- **Tasks are ordered** latest first; tasks with no time come last, in the ledger's order.
- **A deferred part** carries its state from `partState`, and `why` when it is parked.
- **The closing fields** (`closedBy`, `summary`, `commit`) come from `phaseRows`. They are not added to the status, so `board_get` does not grow.

The route, in `repo-api.ts`: `GET /done` answers `DoneWork` from the watcher's current status. It sits in `repoRoutes`, so it is served at `/api/done` and `/api/r/<name>/done` behind the same guard as the others.

Tests first: core tests for each rule above, on a repository built with the existing test support; a server test for the route.

## 6. Part C: ended sessions, read from the activity log

The second function in `done/`:

```ts
interface EndedSession {
  id: string;
  track: string;
  agent: string;
  from: string;
  to: string;
  opened: "recorded" | "first write";
  ended: "closed" | "expired" | "unknown";
  writes: number;
  tasks: string[];
  moreTasks?: number;
}

interface EndedSessions {
  kept: boolean;
  sessions: EndedSession[];
  total: number;
  earlier?: number;
}
```

The rules:

- **A session** is every event in the log with one session id. A session that is still open (`listSessions`) is left out: it is on the board.
- **`from`** is the time of its first event. `opened` is `recorded` when that event is `session_open`, and `first write` otherwise, which is every session from before this build.
- **`to`** is the time of its last event.
- **`ended`** is `closed` when it has a `session_close` event, `expired` when it has a `session_expire` event, and `unknown` otherwise.
- **`writes`** counts its events other than `session_open`, `session_close` and `session_expire`.
- **`tasks`** are the distinct targets of its `task_claim`, `task_land` and `land_start` events, at most 8; `moreTasks` counts the rest.
- **Order and size:** latest `to` first. `limit` keeps the newest (default 50, at most 500); `total` counts them all.
- **The window:** the newest 120 day files are read. `earlier` counts the day files older than that, and is left out when there are none.
- **`kept`** is false when the config does not say `context: "records"` and the log folder is empty; the answer then holds no session.

The route: `GET /done/sessions?limit=<n>`. A `limit` that is not a whole number from 1 to 500 answers 400 with a sentence, as `/graph` does.

Tests first: sessions grouped across two day files; an open session left out; each value of `opened` and `ended`; the limit and the total; more than 8 tasks; a repository with no log; the route's refusal.

## 7. Part D: the activity log records a session's opening and its expiry

Two events are added. Both use the event shape the log has now, so no stored format changes.

- **`session_open`.** `decorators/activity.ts` skips a call with no `sessionId` argument, and `session_open` has none. For that one tool, the session is the one in the result. It is logged where the config says `context: "records"`, like every other event, and has no target.
- **`session_expire`.** `expireSessions` in `state/expire.ts` logs it before it ends the session, with the target `idle <n> min`. It is logged first so that, where the last session's end commits the waiting records, the event is in that commit.

`activity_get`'s description says what the log now holds: one event for each write a tool made, one when a session opens, and `session_expire` when tally closed an idle one. `DESIGN.md` §16.6 says the same.

Tests first: a `session_open` call leaves one event with the new session's id, track and agent; none where the repository keeps no log; a refused `session_open` leaves none; an expired session leaves `session_expire` before its records are committed.

## 9. Part F: the Done view

- **The switch.** `MainView` and `Page` gain `done`. `MAIN_VIEWS` becomes Board, Done, Evidence, Docs; `PAGES` becomes Board, Tracks, Graph, Done, Evidence, Docs. The hero is not drawn on Done, as it is not on Docs.
- **The data.** Two hooks in `live.ts`, fetched only while Done is shown, and again when a new snapshot arrives. Loading more sessions asks for a larger `limit`, as the graph does, so a new snapshot never throws away what the reader has loaded.
- **Inside the view,** a second switch: "Phases and tasks" (the default) and "Sessions".
- **Phases and tasks.** A line of counts first: "1 phase closed · 10 milestones finished · 63 tasks landed". Then one block per phase, folded, the first one open:
  - its heading, as the board writes it, with "closed 2026-11-14" or "open, 84%";
  - for a closed phase: its summary, who closed it, and the commit its records went in with;
  - its milestones, each with a tick when finished or "3 of 5 landed" when in progress, and each folding out to its landed tasks;
  - a task shows its id, its track, its commit (and how many more it has), its date, and its deferred parts with their state. The date's tooltip says whether it was recorded at the landing or is the commit's date.
- **Sessions.** One row per ended session, latest first: the agent, the track, from and to with the length ("10:02 to 11:47, 1 h 45 min"), how it ended ("closed", "expired", or "no close recorded"), how many writes, and its tasks. "Show 50 more" while there are more. Where `earlier` is set, a line says that older sessions are in the activity log. Where `kept` is false, an empty state says that this repository keeps no activity log and that the config's `context: "records"` turns it on.
- **States.** A skeleton while loading, as Evidence has. A failed read says so in a sentence with a "Try again" button; it is never silent. An empty state when nothing is finished yet.
- **Sizes.** Six buttons must fit the phone's bottom bar at 375 px wide without clipping a label. `styles.css` has 308 lines; if the new styles would take it past 400, they go in a file of their own.

Tests first: the switch in both layouts; each state; a closed phase and an open one; a finished milestone and one in progress; a task with a recorded date and one with a commit date; a deferred part of each state; each kind of session ending; loading more; the repository with no log.

## 13. What this plan leaves out

- **A smaller board for agents.** `board_get` could take an option that answers only open work. Measured, its rows would fall from 32.6 kB to 1.4 kB in the first tracked repository and from 54.3 kB to 12.9 kB in the second. It is the largest saving in sight for an agent's context, and it is left out only because the request was about the dashboard. It deserves its own decision.
- **`tally status` in the terminal** still prints every milestone.
- **Closed tracks.** `tracks.json` keeps each one with its purpose and why it closed. They would fit in Done as a third list.
- **Ended sessions for a repository with no activity log.** That would need a stored list, which decision 6 avoids.
- **A bound on `/done`,** by loading a phase's tasks when it is unfolded. Worth doing when a repository has thousands of landed tasks.
- **A smaller snapshot.** The snapshot still carries every milestone and task, although the board no longer draws the finished ones.
- **One word for a phase.** The page says "Stage" where the tools say "phase". Done uses the board's word; choosing one is a separate change.
- **Search and filters in Done.**
